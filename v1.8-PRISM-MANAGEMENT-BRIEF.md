## 1. Inventory — what Prism stores / edits

### 1.1 Azure SQL tables (authoritative)

| Table | Purpose | Key columns |
|-------|---------|-------------|
| **Meta** | Optimistic concurrency for whole-state saves | `StateVersion`, `LastSavedAt`, `LastSavedBy` |
| **Team** | Active roster / billable caps / flags | `TeamId` (am/dp/jr/md), `Name`, `HoursPerWeek` (default 30), **`Flags` JSON** `{capacityExempt, canLead, director}` |

**API surface:** `GET/POST /api/state` (`getState.js` / `saveState.js`). Auth via Static Web Apps Entra (`x-ms-client-principal`). Env: `SQL_CONNECTION_STRING`.  
**Write pattern:** transactional **DELETE-all + INSERT-all** for Customers / Completed / Team / FormerTeam, guarded by `expectedVersion` → 409 on conflict. Hires (`isHire`) are **session-only**, never persisted.

## 3. Recommended architecture

### Decision: **Native Postgres in pimsy-pm (targeted schema + UI). Do not dual-write Prism Azure SQL for MVP.**

**Why (fastest path to manual edits in PM):**

1. **Auth & UI already exist** — Management gate, capacity page, project/customer CRUD, estimator, slip_events. Adding flags + engagement fields is days, not a new data plane.
2. **Prism `saveState` is whole-document** — DELETE+INSERT of all customers/team on every save. Dual-writing from PM would either (a) fight optimistic concurrency with live Prism users, or (b) require risky partial UPDATEs that Prism UI may overwrite on next full save.
3. **Roadmap already sequences dual-read after v1.9** — Director/Pipeline routines keep reading live Prism until Management Capacity → Forecast exist in PM; then dual-read → write cutover → retire purple-beach.
4. **No new Azure SQL secrets / mssql / firewall** on the PM App Service for MVP.

**Rejected for MVP:** Dual-read/write Prism SQL as the write store for roster edits (slower, conflict-prone, delays PM-native truth).

**Optional (post-MVP / ops):** one-shot or nightly **read-only import** from Prism SQL → PM Postgres to refresh drift before cutover (`PRISM_SQL_CONNECTION_STRING` optional). Never use Prism’s full-state POST from PM.

### Schema deltas (suggested migration `0007_prism_management.sql`)

**`user`:**

- `capacity_exempt` boolean NOT NULL DEFAULT false
- `can_lead` boolean NOT NULL DEFAULT true
- `is_director` boolean NOT NULL DEFAULT false
- `prism_team_id` text NULL (unique) — maps am/dp/jr/md

Seed flags to match live Team.Flags (Morgan exempt; Alexander director).

**`project` (or small `project_staffing` 1:1):**

- `co_lead_id` text NULL → user
- `owner_split_percent` int NOT NULL DEFAULT 100
- `custom_hours_per_week` real NULL
- `prism_status` text NULL — `active` \| `pre-kickoff` \| `pipeline`
- `prism_note` text NULL

`project_scope` already covers Forecast+ inputs — engagement edit should upsert scope + project fields together.
